# 2026-08-01 Claude relay-detection research audit

## Current conclusion

No black-box detector can prove an arbitrarily well-sanitized multi-hop route with 100% certainty. The safe target is a calibrated, evidence-tiered verdict that never treats model self-report, an echoed `model` value, or the mere presence of a thinking signature as proof of a direct official channel.

The strongest practical design combines:

1. native transport and error-contract fingerprints;
2. deterministic tokenizer and cache-threshold fingerprints;
3. signed-thinking replay and mutation contracts;
4. context-window boundary tests;
5. cross-protocol contradiction analysis;
6. repeated behavioral profiles only as a secondary signal.

## High-value differential probes adopted

The current CLIProxyAPI implementation reveals relay transformations that can be tested against the official baseline:

- It can inject Claude Code system blocks and a synthetic user ID.
- It can locally calculate `count_tokens` while generation receives additional hidden system content.
- It can automatically add cache breakpoints to requests that did not ask for caching.
- It trims more than four cache breakpoints and normalizes invalid cache TTL ordering.
- It can remove thinking controls when a forced tool choice would be incompatible.
- It can rebuild a `system` role embedded in `messages` into a top-level system prompt.
- It can rename tools, restore names in non-stream and SSE responses, rewrite returned model aliases, and translate stream events.
- It can sanitize, cache, strip, or replay thinking signatures.

These behaviors justify the following official-vs-suspect tests:

| Probe | Official baseline expectation | Relay evidence when different |
|---|---|---|
| Same request through `count_tokens` and `messages` | Exact or near-exact input-token parity | Hidden prompt injection or local tokenizer emulation |
| Two identical large requests without `cache_control` | No cache creation/read usage | Automatic cache rewriting |
| Five explicit cache breakpoints | HTTP 400, maximum four | Relay silently dropped breakpoints |
| `5m` cache block followed by `1h` | HTTP 400 with ordering error | Relay normalized TTLs |
| Middle `system` role | Native role-validation error | Relay rebuilt message layout |
| Thinking plus invalid sampling combination | Native model-generation-specific error | Relay normalized sampling controls |
| Signed thinking replay, missing signature, altered signature, cross-model replay | Model-specific replay contract | Signature stripping, local cache replay, or protocol translation |
| Deterministic mixed-language corpora on `count_tokens` | Exact per-model token vector | Different tokenizer/model or locally approximated count |
| Cache content just below/above documented minimum | Per-model threshold transition | Wrong model family or translated cache implementation |
| Near/over advertised context limit | Accepted near limit, exact native overflow error over limit | Smaller hidden model, truncation, or synthetic limit enforcement |

## Evidence tiers for final verdicts

1. **Direct route evidence:** provider-specific unstripped headers, endpoint surfaces, exact native error contracts, exact tokenizer vectors, native usage parity, and repeated official-baseline agreement.
2. **Claude execution evidence:** signed-thinking and capability behavior showing a Claude-family backend, without claiming direct Anthropic routing.
3. **Translation evidence:** silent normalization, model aliases, cache injection, local token counting, stream/model rewriting, or mixed protocol artifacts.
4. **Behavioral evidence:** repeated response-profile similarity. This can raise or lower confidence but must not override hard protocol contradictions.

For multi-hop paths, report the deepest evidence actually observed. If outer relays strip every inner transport marker, the correct result is `Claude-compatible upstream; exact channel not observable`, not a fabricated provider chain.

## Production statistical policy

Behavioral-distribution evidence is governed by a separate policy from hard protocol evidence:

- enroll at least ten valid official samples per cell before a cell may vote;
- use at least eight cells, prefer forty, and rotate paraphrases, cell order, and per-run nonces;
- calibrate the honest tell-rate on held-out official traffic;
- use a betting e-process for repeated traffic and cross the substitution boundary only when wealth reaches `1 / false_positive_level`;
- report a conservative lower bound for suspected dilution rather than an exact hidden routing fraction;
- if the budget ends before the boundary is crossed, return `inconclusive`, never `authentic`;
- never let a behavioral match erase an exact tokenizer, error-contract, endpoint-surface, or protocol-rewrite contradiction;
- never use behavioral similarity to name Anthropic API, Bedrock, Vertex, Azure, or another physical channel.

The current Anthropic distribution capture is below the ten-samples-per-cell gate because the official credit was exhausted. It is retained as a diagnostic prior and regression fixture, but the runtime must not promote it into a production match/mismatch verdict.

The current Amazon Bedrock integration further narrows what can be proved from payload shape alone: Anthropic documents a Bedrock-hosted `/anthropic/v1/messages` surface with the same Messages API shape. Bedrock does not support the first-party Models, Files, Message Batches, Admin, Compliance, Usage/Cost, or server-side tool surfaces. Those endpoint differences are therefore more useful for channel provenance than a Messages response or thinking signature by itself.

## Official baseline captured in this run

- 630 broad/contract records in the initial capture, later extended to 891 sanitized official records across all seven requested Claude models.
- Exact `/v1/models/{id}` capability metadata, context limits, output limits, thinking modes, tokenizer families, prompt-cache thresholds, error contracts, SSE shapes, tool use, images, structured output, batches, and Files API surface.
- Exact tokenizer vectors for nine fixed mixed-language/code/tool corpora per model.
- Exact `count_tokens` versus generation-usage parity; no hidden cache creation on identical requests without `cache_control`.
- Official rejection contracts for five cache breakpoints, invalid TTL ordering, middle `system` messages, invalid sampling with thinking, bad signatures, missing signatures, and unsupported parameters.
- Fable 5, Opus 5, Sonnet 5, Opus 4.8, and Opus 4.7 reject `temperature` as deprecated; Haiku 4.5 and Opus 4.6 accept it.
- Fable 5, Opus 4.7, and Opus 4.6 returned exact 1M overflow errors; Haiku 4.5 returned the exact 200k overflow error.
- Sonnet 5 accepted a 900,023-token input but produced a refusal, so that record proves capacity only.
- Sonnet 5 accepted 499,999 tokens and correctly recalled three codes placed near the beginning, middle, and end, proving both capacity and retrieval for that probe.
- Behavioral calibration contains 8 to 10 usable text samples per model. It remains secondary evidence because adaptive thinking can consume the output budget and because one Opus 5 retry timed out.

Published list-price arithmetic over the observed usage fields estimates approximately USD 11.37, but this is explicitly not an Anthropic billing statement. The API key does not expose wallet balance, credits, discounts, delayed charges, or account-specific pricing, so the detector must not claim that the wallet reached exactly zero from local arithmetic alone.

## Final credit-exhaustion capture

After the first 630 records, a low-token categorical-distribution run was started using ten `fpverify`-compatible cells across all seven models. It recorded 261 calls: 257 successes before the credit error, the same native 400 contract concurrently on Fable 5 and Opus 5, and two already-in-flight successes that completed after the stop signal. The error was `invalid_request_error` with `Your credit balance is too low to access the Anthropic API`. The scheduler did not dispatch the remaining queue.

The final raw evidence therefore contains 891 records, including 261 categorical-distribution records. Each model has 37 or 38 distribution samples spanning all ten cells, but only three to four samples per cell. The One Token / fpverify methods require at least ten valid samples per cell for threshold verdicts, so the current pairwise JSD values are saved as diagnostic priors only and must not drive production match/mismatch verdicts. The credit-exhaustion error is direct evidence that the fixed credit was consumed; no further billable probes should be attempted with this key.
